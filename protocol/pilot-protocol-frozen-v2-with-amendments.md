## 0. Purpose of the pilot
Test the one unproven assumption Paper #1 rests on: that retrieved failure memory helps a data agent, at matched compute. The pilot is a gate, not a miniature of the full paper. If the gate fails, the paper pivots (Section 9) instead of scaling a null result.

## 1. Frozen claim (do not edit after first run)
"Failure-fingerprinted episodic memory improves pass^k on recurring data-agent failures under schema/data drift, at matched token budget, versus no-memory and versus generic episodic retrieval."
Every experiment in the pilot must test a clause of this sentence. Anything that does not is out of scope for the pilot.

Secondary questions:
- Q1: Does exact fingerprint matching beat embedding-only retrieval on identical recurrences, and lose on mutated recurrences? [Design hypothesis — untested for data agents]
- Q2: Does pre-drift (stale) memory perform worse than no memory on post-drift tasks? [G risk signal: Zhang et al., arXiv:2605.12978v2, consolidated LLM-updated memory degrading below no-memory on general tasks — not data evidence]

## 2. Substrate (evaluation data)
- Primary: BIRD Dev subset + Spider 2.0-Snow subset. [D: BIRD, Li et al., NeurIPS 2023 D&B; Spider 2.0, Lei et al., ICLR 2025 Oral, 632 workflows] — **AMENDED 2026-11-22 (Amendment A1 below): primary pool is BIRD-only; Spider 2.0-Snow is excluded.**
- Labels: Use Jin et al.'s corrected labels where released (arXiv:2601.08778v3; audit found 52.8% annotation errors in BIRD Mini-Dev and 62.8% in Spider 2.0-Snow, rank shifts −9 to +9). Report every result twice: original labels and corrected labels. Pre-commit to this in writing before running.
- Version discipline: Quote Spider 2.0 results with version — arXiv v1 reports 17.0% for the o1-preview agent, v2 / ICLR 2025 reports 21.3%. Never mix versions in one table.
- Exclusions: Any task whose gold SQL is disputed in the Jin audit and has no corrected label is excluded from the pilot's primary metric and listed separately. [Design]

## 3. The two splits to build (the pilot's data work)
### 3a. Repeated-failure split (~60 tasks)
- Cluster tasks by failure class (Section 5 taxonomy, seeded from pilot dry runs, then frozen).
- Order clusters into sessions: Session 1 tasks are attempted first and populate memory; Session 2+ tasks are different tasks that share a failure class with an earlier task (exact recurrence, then paraphrase/mutation of the same class).
- Leakage rule: memory for a task may only contain episodes from strictly earlier sessions. Any violation invalidates that run. [Design]
- Similarity distance (v2): for every Session 2+ task, compute its distance to the Session 1 task(s) sharing its failure class — at minimum: question-embedding similarity, schema-element overlap, and gold-SQL structural overlap. Report all pilot results stratified by distance tertile. Tasks above a pre-set near-duplicate threshold are EXCLUDED from the primary metric and reported separately as a recall control — memory succeeding only on near-duplicates does not support the claim. [Design]
### 3b. Drift split (~40 tasks)
- Take tasks from 3a and apply documented, reversible drift operators. At least half the split must be SILENT drift — the schema looks the same, the meaning changes: (i) value-code remapping under the same column name, (ii) metric-definition change with the same column name, (iii) unit/scale change in stored values, (iv) row-population change that alters what a previously correct filter returns. The remainder is OVERT drift, as a control condition: (v) column rename, (vi) table rename/split, (vii) value-format change. Record the operator, target, and pre/post schema version for every task. Rationale: overt drift is detectable on schema exploration, so an agent can defeat stale memory simply by re-exploring; silent drift is where stale memory can actually cause a wrong answer. Also log the agent's re-exploration behaviour (did it inspect the schema/data before reusing a remembered pattern?) per task. [Design — no public drift split was found in the verified passes, so this split is itself a contribution if released]
- The stale-memory arm (Section 4) runs these tasks with memory populated pre-drift and not updated.

## 4. Arms (all on the same base agent and model)
1. A0 No-memory single agent — control.
2. A1 Failure-memory single agent — the method: fingerprint exact match + contrastive embedding retrieval over raw episodic traces (Section 6). No LLM consolidation/summarisation of memory in the pilot. [Design, justified by the Zhang et al. harm signal, G]
3. A2 Generic episodic memory — MemGPT-style / plain trace RAG retrieval without fingerprinting or failure-class keying. Ablation that isolates the fingerprint contribution.
4. A3 Generate-and-select at equal budget — CHASE-style multi-candidate generation + selection, given the SAME total token budget as A1's average spend. [D precedent: CHASE-SQL, ICLR 2025, 73.01% dev / 73.0% test on BIRD, at explicit extra test-time compute — this arm removes that confound]
5. A4 Stale memory — A1's memory, frozen pre-drift, run only on the drift split. Tests Q2 / negative transfer.
Optional if budget allows: A5 Oracle memory — memory containing the correct remediation for the task's failure class. Upper bound; helps separate retrieval failure from representation failure. [Design]

## 5. Failure-class taxonomy (seed, freeze after dry run)
Seed classes for agent failures, derived from the pilot's own dry-run traces and the failure modes documented in the public benchmarks used here; this is a [Design] taxonomy to be frozen after the dry run, not taken from any prior publication:
- F1 Wrong schema link (wrong table/column)
- F2 Stale schema assumption (pre-drift name/definition used post-drift)
- F3 Wrong join / join fan-out
- F4 Aggregation / grouping error (incl. metric-definition error)
- F5 Value-format / filter literal mismatch
- F6 Execution error not recovered (syntax, dialect, permission)
- F7 Correct SQL, wrong interpretation / answer format
- F8 Unsafe or destructive operation attempted (log only in pilot; no write tasks executed outside sandbox)
Blind labelling (v2): two annotators (or author + one checker) label dry-run traces WITHOUT seeing the seed classes above — open coding first. Only after open coding are the labels reconciled with the seed list; classes that appear in open coding but not the seed are added, seed classes with no observed instances are dropped or marked unobserved, and every change is logged. The reconciled list is the frozen taxonomy. Report inter-annotator agreement (on the open coding) in the pilot report.

## 6. Memory implementation spec (minimal)
- ACQUISITION POLICY (v2 — the pilot's most important rule): An episode may enter retrievable memory ONLY if its remediation was (a) produced by the agent itself during that session, and (b) verified by execution against the task's database at the time (the corrected SQL ran and returned a result the agent's own verifier/check accepted). Gold SQL, corrected labels, and human-written fixes must NEVER be used to create, complete, or repair an episode — that would make memory partly oracle-built and invalidate the comparison. Failures the agent never recovered from are stored in a separate UNRESOLVED log: they are counted and analysed, but they are not injected as remediations. Report, as a headline pilot statistic, the acquisition rate: the fraction of observed failures that ever produce a storable, verified episode. If that rate is low, memory cannot help in deployment either, and that is a finding, not a protocol failure.
- Episode record: task intent (normalised), schema elements touched, SQL/tool trajectory, error observed, failure class (Section 5), the agent-discovered, execution-verified remediation, schema version, timestamp.
- Fingerprint: normalised deterministic key over (failure class, error signature, schema elements, schema version), defined in this protocol for agent traces. [Design]
- Retrieval: (1) exact fingerprint match; else (2) top-k by embedding similarity over episode records; inject at most k=3 episodes, as raw traces, into the prompt. Log retrieval hits/misses and whether the retrieved class matched the eventual failure class.
- Invalidation: schema-version mismatch flags an episode as stale; A1 may still retrieve it but must be logged as a stale retrieval (this is what A4 isolates by forcing stale-only).
- No training / fine-tuning in the pilot. One frontier API model + one open model if budget allows; model, version, and decoding settings frozen and recorded per run.

## 7. Fairness protocol (compute-fair, pre-committed)
- Budget unit: total tokens (input + output, including retrieval injection and all candidate generations) per task. A3's budget is capped at A1's pilot-average; A0 may optionally be run in a second, budget-matched variant (extra self-debug attempts up to the same cap) — if run, report both A0 variants. [Design; G support: Tran & Kiela, arXiv:2604.02460, single agents match/beat MAS at equal thinking-token budgets on general reasoning — not data evidence]
- Token-matching is an approximation, and the protocol says so (v2): the memory arm also changes the prompt distribution (injected context), and the generate-and-select arm spends tokens on parallel candidates rather than sequential reasoning. Therefore BOTH comparisons are mandatory and reported side by side: (a) token-matched — equal total tokens per task; (b) attempt-matched — equal number of SQL attempts / candidate generations per task. A claim of a memory advantage must survive at least the token-matched comparison and be reported honestly under the attempt-matched one.
- Also record wall-clock latency and estimated $ cost per task and per success. [G7 gap: no published data-specific latency/cost for this comparison was found]
- Same prompts (except the memory-injection block), same tools, same sandbox, same max steps across arms.
- Runs per task: 4 runs per task per arm in the pilot (used for variance and for an exploratory pass^k estimate — see Section 8); same count across arms.

## 8. Metrics (primary first)
- PILOT primary (v2): paired pass@1 difference (A1 vs A0, and A1 vs A2) on the repeated-failure split, excluding near-duplicates (Section 3a), stratified by similarity distance. Reason for the change: at ~100 tasks, pass^k (all-runs-succeed) has a low base rate and wide intervals — it cannot gate a pilot honestly. [Metric note: pass@1 here is the mean per-run success rate, paired by task]
- FULL STUDY primary (unchanged claim metric): pass^k on recurring failures. [Metric from tau-bench, Yao et al., arXiv:2406.12045 — G, retail/airline; applying it to data agents is the G3 gap] The pilot reports pass^k with k=4 as an exploratory estimate only, with its confidence interval, and does not gate on it.
- Secondary: memory acquisition rate (Section 6); pass^k on the drift split (A1 vs A4 vs A0, exploratory); recovery rate (failure detected → corrected within the run); retrieval precision (retrieved class = true class); stale-retrieval rate; re-exploration rate on drift tasks; tokens, latency, $ per success; destructive-op attempts (sandbox state diff).
- Statistics and POWER (v2): before the protocol is frozen, run a simulation-based power analysis using ONLY the A0 dry-run base rates (no arm results seen yet): simulate paired task outcomes across plausible effect sizes and discordance rates, and from it set (a) the pilot's minimum detectable effect and (b) the GO margin in Section 9. Record both numbers in the frozen protocol. Report per-arm means with 95% CIs (task-level bootstrap); primary comparison is paired by task. If the power analysis shows the pilot cannot detect a plausible effect at ~100 tasks, increase tasks or runs before freezing — do not freeze an underpowered gate. [Design]

## 9. Stop / pivot rules (pre-committed)
- GO to full study if: A1's paired pass@1 advantage over A0 on recurring failures (near-duplicates excluded) meets or exceeds the GO margin set by the Section 8 power analysis, with paired CI excluding 0, AND A1 is not beaten by A3 under the token-matched comparison AND the drift results show a measurable stale-memory effect in either direction (A4 vs A1 on the drift split, silent-drift subset reported separately).
- PIVOT if memory shows no gain: stop scaling; reframe Paper #1 as the compute-fair / corrected-label evaluation paper (gaps G2+G5 from Step 2 v2) reporting the negative memory result as a finding. Do not quietly change the claim.
- STOP and rethink if: retrieval precision is near chance (representation problem, not an evaluation problem) — fix the fingerprint before any further runs.

## 10. Threats to validity (declare in the pilot report)
- Benchmark label noise (Jin et al.) — mitigated by dual reporting, not eliminated.
- Planted/derived failure classes and synthetic drift may not match production failure distribution — the split construction must be documented so reviewers can judge this.
- Single-vendor model risk if only one model is affordable — say so; do not generalise beyond the models run.
- Independence of the pilot: the pilot stands or falls on its own runs. No result from any prior publication (by the author or anyone else) is assumed or imported.

## 11. Deliverables of the pilot
1. Frozen claim + this protocol (signed off before runs)
2. Repeated-failure split + drift split, with construction documentation (releasable)
3. Run logs: per-task, per-arm, per-run outcomes, tokens, latency, retrievals
4. Pilot report: primary comparison first, dual-label results, taxonomy agreement, stop/pivot decision with the rule that triggered it

## 12. Order of work
1. Freeze claim + protocol (this document) — author sign-off
2. Build substrate: select tasks, apply corrected labels, document exclusions
3. Dry run (~10 tasks, A0 only) → blind-label traces → reconcile → freeze taxonomy; run the Section 8 power analysis from dry-run base rates and record the GO margin
4. Build splits 3a/3b (with similarity distances and silent/overt drift labels)
5. Implement memory (Section 6, incl. acquisition policy) + logging
6. Run pilot (all arms, 4 runs per task)
7. Analyse against Section 9 rules → GO / PIVOT / STOP decision, in writing
